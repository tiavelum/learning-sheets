One change, end to end

A new version of an app travels from a developer's commit to a running store. The markers are the item numbers from pages 1–4.

Build

A developer pushes code. The CI pipeline (6) builds and tests it, packs a new container image (7) and pushes it to the registry (8). CI stops there.

Propose

The update bot (9) sees the new version and opens a pull request (2), or commits directly, changing the image tag in a manifest (3), in Helm values (4) or in a Kustomize overlay (5).

Approve

A colleague reviews and merges. The Git repository (1) now holds the new desired state, recorded with author and time.

Pull

Argo CD (13) or Flux (14), usually running inside the cluster, notices the new commit, renders the Helm chart (4) or Kustomize overlay (5), and applies the result to the Kubernetes API. No CI pipeline needs the cluster's keys.

Admit

The policy engine (11) checks each object before the API stores it. Secrets arrive decrypted inside the cluster (16) or fetched from a secret store (17).

Run

Kubernetes (10) pulls the new image from the registry and replaces the old containers; progressive delivery (15) can do this step by step, watching metrics.

Keep

From now on the agent keeps comparing Git with the cluster. A change made by hand in the cluster is drift and gets flagged or undone. To roll back, revert the commit.

Beneath

Terraform or OpenTofu (18) built the cluster this runs on; Crossplane (19), inside a cluster, adds networks and databases.

Ask of any tool

  1. Where does it work? Writing the plan, building the goods, bringing the plan into the store, or the building.
  2. Push or pull? Does something outside send changes in, or does an agent inside fetch them?
  3. Once or all day? Does it act on command and stop, or keep comparing and correcting?
  4. Who holds the keys? A pipeline outside the cluster, or only an agent that pulls?

Remember

  • GitOps means: desired state in Git, plus an agent that pulls it and keeps correcting. OpenGitOps names four principles: declarative, versioned and immutable, pulled automatically, continuously reconciled.
  • CI builds; the GitOps agent deploys. Neither does the other's job.
  • A change to production is a commit, usually via a merged pull request; a rollback reverts it.
  • Two loops: Argo CD (13) or Flux (14) keep the cluster's objects equal to Git; Kubernetes keeps containers equal to those objects.
  • No secret in plain text in Git: encrypt it (16) or reference it (17).
  • "Pull request" (2) is not pull deployment: one proposes a change to Git, the other is how the cluster fetches from Git.
