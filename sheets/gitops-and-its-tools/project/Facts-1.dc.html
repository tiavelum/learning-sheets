Drawn in the scene · page 1, several places
Git repository
hosted on GitHub, GitLab, Bitbucket
 Files plus their full history; each commit is a fixed snapshot. Holds the desired state: the single source of truth. Passive; agents read one branch. A rollback is a reverted commit. The Git host, which adds pull requests and access rules.
Pull request
merge request in GitLab
 A proposal to merge a branch, with diff, checks and reviews. The usual change gate: review and approval before a change. Once per change; the merge updates the branch the agents watch. A deployment: it changes only Git; an agent applies it.
Manifest
Kubernetes YAML
 A file declaring an object's desired state, e.g. 3 copies of v2.1. Says what should exist, not how to create it (declarative). Applied to the Kubernetes API; a GitOps agent keeps comparing it with the live object. A script, which runs steps once and cannot be compared.
CI pipeline
GitHub Actions, GitLab CI, Jenkins, Tekton
 Automated jobs that run on each code change. Builds, tests and packs the image; pushes it to the registry. Push: a commit triggers it, it runs once, then stops. The deployer: in GitOps, CI never touches the cluster (12).
Container image
built with Docker, Podman, BuildKit
 A read-only bundle of an app and the libraries it needs. Is what runs; manifests name it by tag (v2.1) or digest. Never changes once built; a tag can be moved, a digest cannot. A container, which is one running copy of an image.
Container registry
Docker Hub, GHCR, Harbor, ECR
 A server storing images and other OCI artifacts, e.g. Helm charts. Keeps pushed versions until deleted; clusters pull them. Passive: CI pushes images in, cluster nodes pull them out. The Git repository (1): Git holds the plan, not the goods.
Update bot
Renovate, Dependabot, Argo CD Image Updater, Flux image automation
 A tool that watches for newer image, chart or package versions. Writes the new version into Git, as a commit or a pull request. Polls on a schedule; it must write to Git, not the cluster (Image Updater: write-back git). CI (6): it builds nothing, it only edits version numbers.
Kubernetes cluster
control plane plus worker machines
 Machines run by a control plane whose API stores objects. Keeps containers running as its objects say: restarts, reschedules. Reconciles all the time, but only against its own API; never reads Git. The GitOps agent (13, 14), which keeps those objects matching Git.
Policy engine
Kyverno, OPA Gatekeeper
 A webhook the Kubernetes API calls before storing an object. Rejects or amends objects that break rules, e.g. unknown registries. On matching create, update, delete. Kyverno: YAML or CEL; Gatekeeper: Rego or CEL. Pull-request review (2): it checks at the cluster's door, after Git.
Head office · ways to write plan sheets for many stores
Helm chart
Helm 4
 A versioned package of templated YAML plus default values. Renders manifests from templates and values per environment. The Helm CLI installs and tracks releases; in GitOps, 13 or 14 uses the chart. Kustomize (5): Helm fills blanks; Kustomize patches finished YAML.
Kustomize
built into kubectl
 Patches per environment (overlays) laid over plain YAML. Produces final manifests without a template language. At render time: kubectl apply -k, or inside Argo CD (13) and Flux (14). A package manager: it packages nothing and tracks no releases.
